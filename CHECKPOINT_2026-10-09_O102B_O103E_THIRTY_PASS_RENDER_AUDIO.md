## Core findings

### Packed resource renderer (O102B–O102N)

The authentic code at file physical `0x659C6` consumes a packed resource identifier in the upper eight bits of ESI and a **24-bit source offset** in its lower bits. It references the runtime resource handle table at `0x2F434`. Its row transfer, starting at `0x65A0F`, performs exactly **80 DWORD iterations**, **320 destination bytes** per row, adding a runtime lookup-derived DWORD to each source DWORD rather than simply copying four bytes without transformation. The source base advances **896 bytes** between rows (`+0x380`). A separate global accumulator `0x77477` is incremented by `0x77473` and signed-shifted by 16 when deriving a row-dependent source adjustment. The fill path uses a **0xFA00 (=64,000)-byte destination boundary**. Although this is consistent with a 320×200-sized buffer, it does not by itself establish a final screen mode or stage identity.

Seven native resources contribute **320 packed rows** covering **286,720 source bytes**. There are **320 unique 896-byte rows**, **320 unique first-320-byte portions** and **320 unique remaining-576-byte portions**. The latter are not zero padding; preserving their bytes is mandatory. We did not infer that these bytes are indexed-color palette values, nor that each complete source row itself is directly displayable.

### Other format/consumer boundaries (O102O–O102V)

`VFRAME.GRA`'s 256×100 packed-field path is inside code guarded by a comparison with `2`, and the bounded sequence calls setup `0x81EB2`, then producer `0x81BB3`, then a continuation `0x862A1`. This proves order and a branch guard, not runtime selection over the competing ten-tile interpretation. Cave's 49-image descriptor table has eight authentic Object-2 incoming relocations; the 46×1, 120-byte Cave prefix remains an **unowned decoder candidate**. Fonts prefix, Playsta overlap and Monks integer runs remain structurally held.

### Original DOS `.MID` resources (O102W–O103C)

There are **33 `.MID` files** in `mk2/sound`. All start with byte `0x01`; **none** has a conventional Standard MIDI File `MThd` header or an embedded `MTrk` text marker under the bounded byte scan. The little-endian unsigned 16-bit value at bytes **1–2** differs from the file's exact byte length by **a positive odd number between 7 and 23** in all 33 files. This is a **length-like observation, not a proven encoding specification or event count**. `intro1.mid` alone has byte 3 = `0xB9`; the other 32 use `0x00`. It would be incorrect to interpret bytes 1–3 collectively as a universal 24-bit length; `intro1.mid` falsifies that assumption. All 33 original-file hashes are recorded. `GMI.BIN` and `SCC.BIN` remain byte-identical.

## Falsified or withheld interpretations

1. **Reject:** seven packed suffixes are simply 320-byte rows with 576 bytes of blank padding. Native row tails contain preserved nonzero bytes, and the code uses a 896-byte source stride.
2. **Reject:** all `.MID` files use conventional `MThd`/`MTrk` Standard MIDI File structure. None of the 33 has those markers.
3. **Reject:** interpreting the `.MID` third *payload* byte as a fixed 24-bit length without checking `intro1.mid`.
4. **Withhold:** visual RGB output, resource-to-stage coactivation, scrolling frame rate, actual MIDI event grammar, and further exact-full GRA promotions.
